## ClashX Meta 节点实测出口（诊断，非仓库变更）

- 起因：用户怀疑节点标称地区与实际出口不符（面板「出口 IP」显示 104.18.18.19 与 ip 检测站不一致）。
- 结论一：面板「出口 IP」列 = **本机出站 socket 对端**（节点入口），不是公网出口；104.18.18.19 属 Cloudflare（RDAP: CLOUDFLARENET 104.16.0.0–104.31.255.255），当前选中节点 `CF_V1` 即 CF 中转节点。
- 结论二：`api.ip.sb` 路由链 = `proxy.yaml:159 DOMAIN-SUFFIX,ip.sb` → `config.yaml:865 RULE-SET,proxy,PROXY` → 组 `PROXY`(select) → `手动选择`(select, 162 节点) → `CF_V1`。
- 实测：脚本 `/tmp/test_nodes.py` 遍历 `手动选择` 中 36 个 `S2$` 节点，逐一切换 + `curl -x 127.0.0.1:7893 api.ip.sb/ip` + ip-api 批量查 ASN，跑完还原 CF_V1。报告 `tmp/node-exit-ip.md`。
- 结果：21 成功 / 15 超时；国家级标称 21/21 全对；城市级有偏差（5 个「洛杉矶」中 2 个实际凤凰城 1GSERVERS）；4 个节点共用出口 142.202.240.77；2x倍系列全为 AWS(AS16509)/G-Core(AS199524)/Google，属机房 IP。
- IPv6 节点（5+3 个）全超时：`config.yaml` 中 `dns.ipv6: false` 且 tun 仅 `inet4-address`，非节点故障。
- 环境事实：mixed-port **7893**（非 7890），TUN 开启（utun5/gvisor/198.18.0.1/30），external-controller `127.0.0.1:9090` 无 secret。

## google.com → google.com.hk 跳转（同夜追加）

- 实测 `curl -x 127.0.0.1:7893 https://www.google.com/` 返回 `302`，`location` 含 `pref=hkredirect&pval=yes&hl=zh-CN`；**无 cookie + `Accept-Language: en-US` 仍 302** → 判定纯来自出口 IP 被识别为香港，与语言/缓存无关。
- `谷歌` 组当前 `now=美国_自动回退` → 落 `美国CF-I`（CF 中转节点，出口被 Google 判为 HK）。再次印证「节点名不可信」。
- `https://www.google.com/ncr` 一次写入 NID cookie 后，再访问 `google.com` 返回 **200 不跳转**（实测有效）；但 IP 仍判 HK 时可能压不住，需换真美国机房节点（如 `美国洛杉矶-3-S2` 104.194.8.36 / `美国洛杉矶-4|电信联通优化-S2` 104.238.221.29）。
- **定案（实测对比）**：`🇺🇸美国CF-1` 出口 `23.188.240.197`，GeoIP/RDAP 均为 **US / Illinois / Savoy**（AS19625 Metro Communications，RDAP `ZTVI-V4-1`，ForwardingPlane LLC），节点标「美国」**没错**；但 Google 仍 302 → `google.com.hk`（`pref=hkredirect`），即 **Google 自有 GeoIP 把该 IP 段判成香港**。换 `美国凤凰城|高速下载-S2`（142.202.240.77）与 `美国洛杉矶|高速下载-S2`（104.238.221.29）均返回 **200 不跳**。
- 结论：CF 系节点触发 .hk 跳转属 Google 判定问题，非标错；根治靠避开 CF 系节点（`谷歌` 组不要用 `美国_自动回退`，会落 CF-1）。
